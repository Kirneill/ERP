Architecture Walkthrough for the AEC ERP Demo

This page, along with the dashboard, explains each application layer, why it exists, and how the demo separates UI, API, services, SQL reporting, persistence, validation, and traceability.

30-second setup

I built a local AEC project controls slice with React/Vite, a .NET API, EF Core, SQLite, and a reporting view named vw_project_health.

Candidate opening talk track

I would start here: this is intentionally small, but it is not fake. The frontend is a React/Vite dashboard. The backend is an ASP.NET Core Minimal API. The database is SQLite through EF Core, with a SQL view called vw_project_health. The goal is to show how I turn project controls and integration quality into something an interviewer can inspect live.

Layered architecture

The walkthrough moves top to bottom: user action, API call, service logic, EF Core mapping, SQLite storage, and reporting output. The file is standalone HTML and CSS, with no external scripts, fonts, or assets.

Live demo data flows

1Dashboard load

The dashboard requests project health, summary metrics, recent integration errors, and recent audit logs. If project health fails, it clearly labels demo/offline mode.

2Sample import

The candidate clicks Run sample import. The client posts five ManualImport time-entry rows. The known result is 2 accepted and 3 rejected.

3Validation boundary

The API rejects bad hours, missing work dates, excessive daily hours, unknown project or employee references, missing references, duplicates, and null rows.

4Exception evidence

Rejected rows become integration errors. The frontend can export those errors as an exception report CSV for interviewer review.

5Reset path

The reset endpoint clears mutable import state and restores deterministic seed audit evidence, so the walkthrough can be repeated cleanly.

Database model summary

Project controls
  • ClientsOwner/client records and market sector context.
  • ProjectsProject number, manager, status, contract value, cost to date, estimate at completion, dates, and percent complete.
  • ResourceAssignmentsEmployee project roles and planned hours.
Integration activity
  • EmployeesEmployee number, name, and email for import validation.
  • TimeEntriesAccepted external rows with unique external references.
  • ImportBatchesSource system, row totals, accepted count, rejected count, start time, and completion time.
Traceability and reporting
  • IntegrationErrorsRejected import rows with context, severity, message, and details.
  • AuditLogsAccepted imports, batch completion, seed activity, and reset evidence.
  • vw_project_healthSQL view consumed through EF Core for reporting-style project health rows.

Design decisions and production tradeoffs

SQLite for portability

SQLite keeps the project cloneable for interviews. EF Core keeps the data boundary close to a production implementation.

Minimal API for focus

The .NET API stays small and readable, which makes it easy to inspect routes, validation, service calls, and response shapes live.

No auth in the demo

The slice is local-only. Production would need SSO, RBAC, tenant isolation, secure audit retention, and environment controls.

Production next steps

Add real connectors, background jobs, retries, dead-letter workflows, observability, deployment automation, and compliance-grade audit controls.
