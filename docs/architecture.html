Architecture — AEC ERP Demo

A portable local stack that keeps the demo easy to clone while preserving the same boundaries a production ERP integration would use: UI, API client, Minimal API, services, EF Core, SQLite tables, and a reporting view.

Core path

React dashboard → API client → ASP.NET Core Minimal API → services → EF Core → SQLite tables + vw_project_health.

Data flow cards

1Dashboard load

Frontend requests project health, recent integration errors, and recent audit logs. If the project-health request fails, the dashboard shows an explicit offline/demo fallback.

2Sample import

User clicks Run sample import. The API client posts five ManualImport time-entry rows. The backend returns accepted and rejected counts.

3Validation failure

Invalid rows are rejected for bad hours, missing work date, excessive daily hours, unknown project/employee, missing reference, duplicate reference, or null row.

4Audit traceability

Accepted rows become time entries and audit logs. Rejected rows become integration errors and can be downloaded as an exception report CSV.

5Reset demo data

The reset endpoint clears mutable import state and restores the deterministic seed audit log, keeping repeated interviews predictable.

Design decisions and tradeoffs

SQLite for portability

SQLite keeps the demo cloneable and local, while EF Core preserves a production-like data access boundary. Production would move to managed storage with migrations, backup, and monitoring.

Local demo reset

/api/demo/reset intentionally clears mutable rows so interview runs stay predictable after imports, testing, or experimentation.

No auth because local-only

Authentication and authorization are excluded to keep the interview slice focused. Production would need SSO, RBAC, tenant isolation, and audit retention controls.

Production next steps

Add real connectors, background jobs, retry/dead-letter handling, observability, deployment automation, role workflows, and compliance-grade audit controls.
